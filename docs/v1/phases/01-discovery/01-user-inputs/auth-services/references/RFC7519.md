## Abstract (บทคัดย่อ)

JSON Web Token (JWT) คือวิธีการแสดง claim ที่ compact และ URL-safe เพื่อถ่ายโอนระหว่างสองฝ่าย claim ใน JWT ถูก encode เป็น JSON object ที่ใช้เป็น payload ของโครงสร้าง JSON Web Signature (JWS) หรือเป็น plaintext ของโครงสร้าง JSON Web Encryption (JWE) ทำให้ claim สามารถถูก sign ด้วย digital signature, ป้องกันความสมบูรณ์ด้วย Message Authentication Code (MAC) และ/หรือ encrypt ได้

> **การออกเสียง:** JWT ออกเสียงเหมือนคำภาษาอังกฤษว่า **"jot"**

## 1. Introduction

JSON Web Token (JWT) เป็นรูปแบบการแสดง claim ที่ compact ออกแบบมาสำหรับสภาพแวดล้อมที่มีพื้นที่จำกัด เช่น HTTP Authorization header และ URI query parameter

JWT encode claim ที่จะส่งเป็น JSON object ซึ่งใช้เป็น:
- **payload** ของโครงสร้าง JSON Web Signature (JWS) — สำหรับการ sign หรือ MAC
- **plaintext** ของโครงสร้าง JSON Web Encryption (JWE) — สำหรับการ encrypt

JWT แสดงผลโดยใช้ JWS Compact Serialization หรือ JWE Compact Serialization เสมอ

### 1.1. Notational Conventions

คำสำคัญอย่าง "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHOULD", "RECOMMENDED", "MAY", และ "OPTIONAL" ในเอกสารนี้ให้ตีความตาม [RFC2119]

## 2. Terminology (คำศัพท์)

### คำศัพท์ที่นิยามใน specification นี้

| คำศัพท์ | ความหมาย |
|---------|----------|
| **JSON Web Token (JWT)** | String ที่แสดงชุด claim เป็น JSON object ที่ encode ใน JWS หรือ JWE ทำให้ claim สามารถถูก sign, MAC และ/หรือ encrypt ได้ |
| **JWT Claims Set** | JSON object ที่บรรจุ claim ที่ JWT ส่งไป |
| **Claim** | ข้อมูลที่ยืนยัน (assert) เกี่ยวกับ subject แสดงเป็น name/value pair |
| **Claim Name** | ส่วน name ของ claim เป็น string เสมอ |
| **Claim Value** | ส่วน value ของ claim สามารถเป็น JSON value ใดก็ได้ |
| **Nested JWT** | JWT ที่มีการ sign และ/หรือ encrypt ซ้อนกัน โดย JWT ถูกใช้เป็น payload หรือ plaintext ของโครงสร้าง JWS หรือ JWE ที่ครอบอยู่ |
| **Unsecured JWT** | JWT ที่ claim ไม่ได้รับการป้องกัน integrity หรือ encrypt |
| **Collision-Resistant Name** | ชื่อใน namespace ที่ออกแบบให้มีโอกาสน้อยมากที่จะชนกับชื่ออื่น เช่น Domain Names, OIDs, UUIDs |
| **StringOrURI** | JSON string value ที่ถ้ามีอักขระ ":" ต้องเป็น URI ตาม RFC3986 และเปรียบเทียบแบบ case-sensitive |
| **NumericDate** | JSON numeric value แสดงจำนวนวินาทีนับจาก `1970-01-01T00:00:00Z UTC` (Unix Epoch) ไม่นับ leap second |

### คำศัพท์จาก specification อื่น

- **JWS:** JSON Web Signature — กำหนด Base64url Encoding, Header Parameter, JOSE Header, JWS Compact Serialization, JWS Payload, JWS Signature
- **JWE:** JSON Web Encryption — กำหนด Content Encryption Key (CEK), JWE Compact Serialization, JWE Encrypted Key, JWE Initialization Vector
- **Digital Signature, MAC, Ciphertext, Plaintext:** กำหนดใน Internet Security Glossary [RFC4949]

## 3. JSON Web Token (JWT) Overview

JWT แสดงชุด claim เป็น JSON object ที่ encode ใน JWS และ/หรือ JWE JSON object นี้คือ **JWT Claims Set** ซึ่งประกอบด้วย name/value pair ตั้งแต่ศูนย์คู่ขึ้นไป

**โครงสร้างของ JWT:**
- **JOSE Header** — อธิบาย cryptographic operation ที่ใช้กับ JWT Claims Set
  - ถ้าเป็น JWS: claim ถูก sign หรือ MAC
  - ถ้าเป็น JWE: claim ถูก encrypt
- JWT แสดงเป็น sequence ของ URL-safe parts คั่นด้วยอักขระ `.` (period)
- แต่ละ part เป็น base64url-encoded value

```
Header.Payload.Signature
```

### 3.1. Example JWT

#### JOSE Header ตัวอย่าง

JWT ที่ใช้ HMAC SHA-256 algorithm:

```json
{
  "typ": "JWT",
  "alg": "HS256"
}
```

Base64url encoding ของ JOSE Header:
```
eyJ0eXAiOiJKV1QiLA0KICJhbGciOiJIUzI1NiJ9
```

#### JWT Claims Set ตัวอย่าง

```json
{
  "iss": "joe",
  "exp": 1300819380,
  "http://example.com/is_root": true
}
```

Base64url encoding ของ JWT Claims Set (JWS Payload):
```
eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFtcGxlLmNvbS9pc19yb290Ijp0cnVlfQ
```

#### JWS Signature (ใช้ HMAC SHA-256)
```
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

#### JWT สมบูรณ์ (3 ส่วนคั่นด้วย `.`)
```
eyJ0eXAiOiJKV1QiLA0KICJhbGciOiJIUzI1NiJ9
.
eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFtcGxlLmNvbS9pc19yb290Ijp0cnVlfQ
.
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

## 4. JWT Claims

**JWT Claims Set** แสดง JSON object ที่สมาชิกคือ claim ที่ JWT ส่งไป

กฎสำคัญ:
- Claim Name ใน JWT Claims Set ต้อง **unique**
- Claim ที่ไม่เข้าใจต้อง **ignore** (ถ้าไม่มี requirement เฉพาะ)
- JWT Claim Name มี 3 ประเภท: Registered, Public, Private

---

### 4.1. Registered Claim Names

Claim Name เหล่านี้ register ใน IANA "JSON Web Token Claims" registry ชื่อถูกออกแบบให้สั้นเพราะ JWT ต้องการความ compact การใช้ claim เหล่านี้ล้วน **OPTIONAL** ทั้งหมด

| Claim | ชื่อเต็ม | ประเภทค่า | รายละเอียด |
|-------|---------|----------|------------|
| `iss` | Issuer | StringOrURI | ระบุ principal ที่ออก JWT การประมวลผลขึ้นกับ application เปรียบเทียบแบบ case-sensitive |
| `sub` | Subject | StringOrURI | ระบุ principal ที่เป็น subject ของ JWT ค่าต้อง unique ใน context ของ issuer หรือ globally unique |
| `aud` | Audience | StringOrURI / Array | ระบุผู้รับที่ JWT มุ่งหมายให้ ถ้า principal ที่ประมวลผลไม่ระบุตัวเองใน `aud` ต้อง reject JWT |
| `exp` | Expiration Time | NumericDate | เวลาที่หมดอายุ — JWT ต้องไม่รับหลังจากเวลานี้ อนุญาตให้มี leeway เล็กน้อยสำหรับ clock skew |
| `nbf` | Not Before | NumericDate | เวลาที่เริ่มใช้ได้ — JWT ต้องไม่รับก่อนเวลานี้ อนุญาตให้มี leeway เล็กน้อยสำหรับ clock skew |
| `iat` | Issued At | NumericDate | เวลาที่ JWT ถูกออก ใช้ระบุอายุของ JWT |
| `jti` | JWT ID | String (case-sensitive) | unique identifier ของ JWT ใช้ป้องกัน replay attack ต้องไม่ซ้ำกันระหว่าง issuer หลายราย |

#### ตัวอย่างการใช้ Registered Claims

```json
{
  "iss": "https://auth.example.com",
  "sub": "user_123456",
  "aud": "https://api.example.com",
  "exp": 1735689600,
  "nbf": 1735686000,
  "iat": 1735686000,
  "jti": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

---

### 4.2. Public Claim Names

Claim Name ที่กำหนดโดยผู้ใช้ JWT ทั่วไป เพื่อป้องกัน collision ควร:
- Register ใน IANA "JSON Web Token Claims" registry หรือ
- ใช้ Collision-Resistant Name (เช่น ใส่ domain name นำหน้า)

#### ตัวอย่าง Public Claim

```json
{
  "https://example.com/roles": ["admin", "editor"],
  "https://example.com/department": "engineering"
}
```

---

### 4.3. Private Claim Names

Claim Name ที่ producer และ consumer ตกลงกันใช้เอง ไม่ใช่ Registered หรือ Public Claim Name ควรใช้ด้วยความระมัดระวังเพราะอาจเกิด collision ได้

#### ตัวอย่าง Private Claim

```json
{
  "employee_id": "EMP-00123",
  "access_level": 3
}
```

## 5. JOSE Header

สมาชิกของ JOSE Header อธิบาย cryptographic operation ที่ใช้กับ JWT และ property เพิ่มเติมของ JWT

### 5.1. "typ" (Type) Header Parameter

ใช้โดย JWT application เพื่อประกาศ media type ของ JWT

- **RECOMMENDED** ให้ตั้งค่าเป็น `"JWT"` เมื่อ object เป็น JWT
- **RECOMMENDED** ให้เขียนด้วยตัวพิมพ์ใหญ่ทั้งหมด (`"JWT"`) เพื่อ compatibility กับ legacy implementation
- **OPTIONAL** — ไม่จำเป็นต้องใช้เมื่อ application ทราบแล้วว่า object เป็น JWT
- JWT implementation จะ ignore parameter นี้ การประมวลผลทำโดย application

```json
{
  "typ": "JWT",
  "alg": "HS256"
}
```

---

### 5.2. "cty" (Content Type) Header Parameter

ใช้เพื่อสื่อข้อมูล structural เกี่ยวกับ JWT

- **NOT RECOMMENDED** ในกรณีปกติที่ไม่มีการ sign หรือ encrypt ซ้อนกัน
- **MUST** มีค่าเป็น `"JWT"` เมื่อใช้ Nested JWT (มีการ sign หรือ encrypt ซ้อนกัน) เพื่อระบุว่า JWT ซ้อนอยู่ใน JWT อื่น

```json
{
  "alg": "RSA1_5",
  "enc": "A128CBC-HS256",
  "cty": "JWT"
}
```

---

### 5.3. Replicating Claims as Header Parameters

ใน encrypted JWT บางกรณี อาจจำเป็นต้องมี claim บางส่วนในรูปแบบที่ไม่ encrypted เพื่อให้ application ตัดสินใจว่าจะประมวลผล JWT อย่างไรก่อน decrypt

specification นี้อนุญาตให้ replicate claim จาก JWT Claims Set เป็น Header Parameter ใน JWE ได้ โดย:
- Application ที่รับควร verify ว่า value เหมือนกัน
- Claim ที่ replicate ต้องปลอดภัยสำหรับการส่งแบบไม่ encrypted

Header Parameter ที่ register สำหรับจุดประสงค์นี้: `iss`, `sub`, `aud`

## 6. Unsecured JWTs

รองรับ use case ที่เนื้อหา JWT ถูกรักษาความปลอดภัยด้วยวิธีอื่นนอก JWT เอง

**Unsecured JWT** คือ JWS ที่:
- `alg` Header Parameter มีค่าเป็น `"none"`
- JWS Signature เป็น empty string

### 6.1. Example Unsecured JWT

**JOSE Header:**
```json
{
  "alg": "none"
}
```

Base64url encoding:
```
eyJhbGciOiJub25lIn0
```

**JWT Claims Set:**
```json
{
  "iss": "joe",
  "exp": 1300819380,
  "http://example.com/is_root": true
}
```

**JWT สมบูรณ์** (สังเกตว่า signature เป็น empty string — มี `.` ต่อท้าย):
```
eyJhbGciOiJub25lIn0
.
eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFtcGxlLmNvbS9pc19yb290Ijp0cnVlfQ
.
```

> ⚠️ **คำเตือน:** Unsecured JWT ไม่มีการป้องกัน integrity ใด ๆ ควรใช้เฉพาะในบริบทที่ปลอดภัยอยู่แล้ว

## 7. Creating and Validating JWTs

### 7.1. Creating a JWT (การสร้าง JWT)

ขั้นตอนการสร้าง JWT มีดังนี้:

**ขั้นตอนที่ 1:** สร้าง JWT Claims Set ที่มี claim ที่ต้องการ

**ขั้นตอนที่ 2:** ให้ Message เป็น octet ของ UTF-8 representation ของ JWT Claims Set

**ขั้นตอนที่ 3:** สร้าง JOSE Header ที่มี Header Parameter ที่ต้องการ (JWT ต้องตาม JWS หรือ JWE specification)

**ขั้นตอนที่ 4:** ขึ้นอยู่กับว่า JWT เป็น JWS หรือ JWE:
- **ถ้าเป็น JWS:** สร้าง JWS โดยใช้ Message เป็น JWS Payload ทำตามขั้นตอนทั้งหมดใน [JWS]
- **ถ้าเป็น JWE:** สร้าง JWE โดยใช้ Message เป็น plaintext ทำตามขั้นตอนทั้งหมดใน [JWE]

**ขั้นตอนที่ 5:** ถ้าจะทำ nested signing หรือ encryption ให้ใช้ JWS หรือ JWE เป็น Message แล้วกลับไปขั้นตอนที่ 3 โดยใส่ `"cty": "JWT"` ใน JOSE Header ใหม่

**ขั้นตอนที่ 6:** JWT ที่ได้คือ JWS หรือ JWE นั้น

---

### 7.2. Validating a JWT (การ validate JWT)

ถ้าขั้นตอนใดล้มเหลว JWT ต้องถูก **reject** ทันที

**ขั้นตอนที่ 1:** ตรวจสอบว่า JWT มีอักขระ `.` (period) อย่างน้อยหนึ่งตัว

**ขั้นตอนที่ 2:** ให้ Encoded JOSE Header เป็นส่วนของ JWT ก่อน `.` แรก

**ขั้นตอนที่ 3:** Base64url decode Encoded JOSE Header (ห้ามมี line break, whitespace หรืออักขระอื่นเพิ่มเติม)

**ขั้นตอนที่ 4:** ตรวจสอบว่าผล decode เป็น UTF-8 JSON object ที่ถูกต้องตาม RFC 7159 — ให้เป็น JOSE Header

**ขั้นตอนที่ 5:** ตรวจสอบว่า JOSE Header มีเฉพาะ parameter และ value ที่ syntax และ semantics เข้าใจและรองรับ

**ขั้นตอนที่ 6:** ระบุว่า JWT เป็น JWS หรือ JWE

**ขั้นตอนที่ 7:** ขึ้นอยู่กับประเภท:
- **JWS:** ทำตามขั้นตอนใน [JWS] สำหรับการ validate ให้ Message เป็น base64url decoded JWS Payload
- **JWE:** ทำตามขั้นตอนใน [JWE] สำหรับการ validate ให้ Message เป็น plaintext ที่ได้

**ขั้นตอนที่ 8:** ถ้า JOSE Header มี `"cty": "JWT"` แสดงว่า Message คือ JWT ที่ซ้อนกัน ให้กลับไปขั้นตอนที่ 1 โดยใช้ Message เป็น JWT

**ขั้นตอนที่ 9:** Base64url decode Message

**ขั้นตอนที่ 10:** ตรวจสอบว่าผล decode เป็น UTF-8 JSON object ที่ถูกต้องตาม RFC 7159 — ให้เป็น JWT Claims Set

> **หมายเหตุ:** แม้ JWT จะผ่านการ validate ได้สำเร็จ application ควร reject JWT ถ้า algorithm ที่ใช้ไม่เป็นที่ยอมรับของ application

---

### 7.3. String Comparison Rules

- การเปรียบเทียบ string ใน JSON ทำตาม Section 8.3 ของ RFC 7159
- กฎเหล่านี้ใช้กับ JSON string comparison ทั้งหมด ยกเว้นสมาชิก `"typ"` และ `"cty"` ที่ไม่ใช้กฎเหล่านี้

## 8. Implementation Requirements

### Signature และ MAC Algorithms

| Algorithm | ข้อกำหนด |
|-----------|----------|
| **HMAC SHA-256 (`HS256`)** | MUST implement |
| **`none`** (Unsecured) | MUST implement |
| **RSASSA-PKCS1-v1_5 + SHA-256 (`RS256`)** | RECOMMENDED |
| **ECDSA P-256 + SHA-256 (`ES256`)** | RECOMMENDED |
| อื่น ๆ | OPTIONAL |

### Encryption Algorithms (OPTIONAL — ถ้า implement ต้องรองรับ)

| Algorithm | ข้อกำหนด |
|-----------|----------|
| **RSAES-PKCS1-v1_5 + 2048-bit keys (`RSA1_5`)** | MUST |
| **AES Key Wrap 128-bit (`A128KW`)** | MUST |
| **AES Key Wrap 256-bit (`A256KW`)** | MUST |
| **AES-CBC + HMAC SHA-256 (`A128CBC-HS256`)** | MUST |
| **AES-CBC + HMAC SHA-512 (`A256CBC-HS512`)** | MUST |
| **ECDH-ES (`ECDH-ES+A128KW`, `ECDH-ES+A256KW`)** | RECOMMENDED |
| **AES-GCM 128-bit (`A128GCM`)** | RECOMMENDED |
| **AES-GCM 256-bit (`A256GCM`)** | RECOMMENDED |
| อื่น ๆ | OPTIONAL |

### Nested JWTs

- รองรับ Nested JWT เป็น **OPTIONAL**

## 9. Security Considerations

### 9.1. Trust Decisions

เนื้อหาของ JWT ไม่สามารถพึ่งพาสำหรับการตัดสินใจด้าน trust ได้ เว้นแต่เนื้อหาถูกรักษาความปลอดภัยด้วย cryptography และผูกกับบริบทที่จำเป็น key ที่ใช้ sign และ/หรือ encrypt JWT มักต้องตรวจสอบได้ว่าอยู่ภายใต้การควบคุมของ party ที่ระบุเป็น issuer

### 9.2. Signing and Encryption Order

สำหรับ Nested JWT ที่ต้องทั้ง sign และ encrypt:
- **แนะนำ:** sign ก่อน แล้วค่อย encrypt (encrypt signature ด้วย)
- เหตุผล: ป้องกันการโจมตีที่ signature ถูกลบออก และให้ privacy กับ signer
- **ข้อพึงระวัง:** signature บน encrypted text ไม่ถือว่า valid ในหลาย jurisdiction

### ข้อพิจารณาด้าน Security เพิ่มเติม

- ต้องปกป้อง asymmetric private key และ symmetric secret key ของ user
- ต้องใช้มาตรการป้องกัน (countermeasures) ต่อการโจมตีรูปแบบต่าง ๆ
- Security consideration ทั้งหมดใน JWS specification ใช้กับ JWT ด้วย รวมถึง JWE security consideration เมื่อใช้ encryption
- ต้อง validate algorithm ที่ใช้และ verify signature เสมอ
- อย่าเก็บข้อมูล sensitive ใน JWT ที่ไม่ถูก encrypt เพราะ header และ payload อ่านได้จาก base64url decode ทั่วไป

---

## 10. Privacy Considerations

JWT อาจมีข้อมูลที่ sensitive ต่อ privacy เมื่อเป็นเช่นนั้น:
- ต้องใช้มาตรการป้องกันการเปิดเผยข้อมูลให้แก่ผู้ที่ไม่ได้รับอนุญาต
- วิธีการที่ใช้ได้:
  1. ใช้ encrypted JWT และ authenticate ผู้รับ
  2. ส่ง JWT ผ่าน protocol ที่ใช้ encryption และรองรับ endpoint authentication เช่น TLS
  3. **วิธีที่ง่ายที่สุด:** ไม่ใส่ข้อมูล sensitive ใน JWT เลย

## สรุปภาพรวม JWT

### โครงสร้าง JWT

```
HEADER.PAYLOAD.SIGNATURE
  │       │        │
  │       │        └─ Base64url(HMAC/RSA/ECDSA signature)
  │       └─ Base64url(JSON Claims Set)
  └─ Base64url(JSON: {"alg":"...", "typ":"JWT"})
```

### Use Cases หลัก

| Use Case | รายละเอียด |
|----------|------------|
| **Authentication** | หลัง user login ออก ID token เป็น JWT (ตาม OpenID Connect) |
| **Authorization** | ส่ง access token เป็น JWT ใน HTTP header เพื่อเข้าถึง API |
| **Information Exchange** | แลกเปลี่ยนข้อมูลที่ verified ระหว่าง service |

### Signing Algorithms ที่รองรับ

| Algorithm | ประเภท | คำอธิบาย |
|-----------|--------|----------|
| `HS256`, `HS384`, `HS512` | HMAC (symmetric) | ใช้ secret key เดียวกันทั้ง sign และ verify |
| `RS256`, `RS384`, `RS512` | RSA (asymmetric) | ใช้ private key sign, public key verify |
| `ES256`, `ES384`, `ES512` | ECDSA (asymmetric) | คล้าย RSA แต่ใช้ elliptic curve — key size เล็กกว่า |
| `none` | ไม่มี | Unsecured JWT — ไม่มี signature |
