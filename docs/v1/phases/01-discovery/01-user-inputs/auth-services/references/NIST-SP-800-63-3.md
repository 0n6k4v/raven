# NIST SP 800-63-3: Digital Identity Guidelines
### แนวทางปฏิบัติด้าน Digital Identity

> **หมายเหตุ:** SP 800-63-3 ถูกแทนที่โดย [NIST SP 800-63-4](https://pages.nist.gov/800-63-4/) ตั้งแต่วันที่ 1 สิงหาคม 2568 (2025) แล้ว กรุณาอ้างอิงเอกสารฉบับใหม่สำหรับแนวทางที่เป็นปัจจุบัน

---

## ภาพรวม

**NIST Special Publication 800-63-3** คือชุดแนวทางปฏิบัติทางเทคนิคสำหรับหน่วยงานรัฐบาลกลางของสหรัฐอเมริกาในการพัฒนาและดูแล digital identity service โดยมีจุดประสงค์เพื่อ:

- กำหนด requirement ทางเทคนิคสำหรับ identity proofing, registration, authenticator, กระบวนการจัดการ, authentication protocol, federation และ assertion ที่เกี่ยวข้อง
- ครอบคลุมการพิสูจน์ตัวตนและการ authenticate ผู้ใช้ (เช่น พนักงาน, ผู้รับเหมา, หรือบุคคลทั่วไป) ที่ติดต่อกับระบบ IT ของรัฐผ่านเครือข่ายสาธารณะ
- แทนที่ NIST SP 800-63-2 ฉบับเดิม

เอกสารฉบับนี้ถูกพัฒนาร่วมกับชุมชนผ่าน GitHub และได้รับความคิดเห็นกว่า **1,400 รายการ** พร้อมผู้เยี่ยมชมเว็บไซต์กว่า **74,000 คน** ระหว่างปี 2559–2560

## แนวคิดหลัก: Digital Identity คืออะไร

**Digital identity** คือตัวตนออนไลน์ของบุคคลหรือหน่วยงาน บุคคลหนึ่งอาจมี digital identity หลายชุด เช่น สำหรับอีเมล, บัญชีการเงิน, หรือระบบขององค์กร

กระบวนการ digital identity แบ่งออกเป็นสามส่วนหลัก:

1. **Identity Proofing** — การพิสูจน์และยืนยันว่าตัวตนที่อ้างนั้นมีอยู่จริง และเป็นของบุคคลนั้นจริง ช่วยป้องกันการสร้างบัญชีปลอม
2. **Digital Authentication** — การตรวจสอบตัวตนของผู้ใช้ทุกครั้งที่เข้าถึงระบบหรือทำธุรกรรมออนไลน์
3. **Federated Identity Management** — กลไกในการเชื่อมโยงตัวตนข้ามองค์กร ทำให้ผู้ใช้ authenticate ครั้งเดียวแล้วเข้าถึงหลาย relying party ได้

## ระดับความน่าเชื่อถือ (Assurance Levels)

SP 800-63-3 แยก **level of assurance** เดิมออกเป็นสามส่วนอิสระ เพื่อให้สามารถเลือก level ที่เหมาะสมกับความเสี่ยงในแต่ละมิติได้อย่างยืดหยุ่น

### 1. Identity Assurance Level (IAL) — ความน่าเชื่อถือของ Identity Proofing

กำหนดว่าตัวตนที่อ้างนั้นได้รับการพิสูจน์อย่างเข้มงวดแค่ไหน (กำหนดใน SP 800-63A)

| ระดับ | ลักษณะ |
|---|---|
| **IAL1** | ไม่ต้องพิสูจน์ว่าตรงกับบุคคลจริง attribute ทั้งหมดเป็น self-asserted (เช่น บัญชี social media ทั่วไป) |
| **IAL2** | ต้องยื่นหลักฐานพิสูจน์ตัวตน สามารถทำแบบ remote หรือ in-person ก็ได้ |
| **IAL3** | เข้มงวดสูงสุด ต้องมาแสดงตนทางกายภาพหรือผ่าน supervised remote session พร้อมเปรียบเทียบ biometric กับหลักฐานตัวตนที่แข็งแกร่งที่สุด |

### 2. Authenticator Assurance Level (AAL) — ความน่าเชื่อถือของกระบวนการ Authentication

กำหนดความเข้มแข็งของกระบวนการ authenticate และการผูก authenticator กับตัวตน (กำหนดใน SP 800-63B)

| ระดับ | ลักษณะ |
|---|---|
| **AAL1** | ต้องการ authenticator อย่างน้อยหนึ่งตัว ป้องกันการโจมตีทั่วไป |
| **AAL2** | ต้องการ multi-factor authentication เพื่อความปลอดภัยสูงขึ้น |
| **AAL3** | เข้มงวดสูงสุด ต้องใช้ hardware-based authenticator และการพิสูจน์การครอบครองผ่าน cryptographic protocol |

### 3. Federation Assurance Level (FAL) — ความน่าเชื่อถือของ Federation Protocol

กำหนดความเข้มแข็งของ assertion protocol ที่ใช้ส่งข้อมูล authentication และ attribute ระหว่างระบบ (กำหนดใน SP 800-63C) — ใช้เฉพาะระบบที่มี federated identity architecture

| ระดับ | ลักษณะ |
|---|---|
| **FAL1** | Assertion ลงนาม (signed) โดย Credential Service Provider (CSP) |
| **FAL2** | Assertion ถูกเข้ารหัส (encrypted) เพิ่มเติมจาก FAL1 |
| **FAL3** | ผู้ถือ assertion ต้องพิสูจน์การครอบครอง cryptographic key ด้วย |

> เมื่อกล่าวถึงรวมกัน เอกสารจะเรียก IAL, AAL, และ FAL ว่า **xAL**

## ผู้เกี่ยวข้องในโมเดล Digital Identity

| ผู้เกี่ยวข้อง | บทบาท |
|---|---|
| **Applicant** | บุคคลที่ขอรับการ identity proof จาก CSP |
| **Subscriber** | บุคคลที่ผ่านการ identity proof แล้ว และลงทะเบียนกับ CSP |
| **Credential Service Provider (CSP)** | หน่วยงานที่ออก credential และจัดการ authenticator |
| **Verifier** | หน่วยงานที่ตรวจสอบ authenticator และ assertion |
| **Relying Party (RP)** | หน่วยงานที่ใช้ผลลัพธ์จากการ authenticate เพื่ออนุมัติการเข้าถึงบริการ |
| **Identity Provider (IdP)** | ผู้ให้บริการ federated identity ในระบบที่มี federation |

กระบวนการทำงานหลักคือ: applicant ผ่าน identity proofing กลายเป็น subscriber → CSP ออก authenticator → subscriber ใช้ authenticator เพื่อ authenticate → verifier ตรวจสอบ → ส่ง assertion ให้ RP → RP ตัดสินใจให้สิทธิ์เข้าถึง

## เล่มที่ 1 — SP 800-63-3: Digital Identity Guidelines (ภาพรวม)

เล่มนี้เป็น top-level document ที่ครอบคลุม:
- กรอบแนวคิด digital identity และโมเดลความเสี่ยง
- แนวทางการเลือก IAL, AAL, และ FAL ให้เหมาะสมกับแต่ละบริการ
- หลักการด้าน privacy: ส่งเสริมการเข้าถึงแบบ pseudonymous และจำกัดการเก็บข้อมูลส่วนบุคคลให้น้อยที่สุด
- แนวทางสำหรับระบบที่ไม่ใช่ federated (เลือก IAL + AAL) และระบบ federated (เลือก IAL + AAL + FAL)

---

## เล่มที่ 2 — SP 800-63A: Enrollment and Identity Proofing

เล่มนี้กำหนด requirement สำหรับกระบวนการ identity proofing และ enrollment ครอบคลุม:

- วิธีพิสูจน์ว่าตัวตนที่อ้างนั้นมีอยู่จริงในโลกกายภาพ
- ประเภทและระดับของหลักฐาน (evidence) ที่ยอมรับได้
- กระบวนการ remote identity proofing กับ in-person identity proofing
- Conformance criteria สำหรับ IAL แต่ละระดับ

**ตัวอย่างในชีวิตจริง:** การที่ DMV กำหนดให้มาแสดงตนเพื่อขอ driver's license หรืออัปเกรดเป็น REAL ID คือตัวอย่างของ IAL3

---

## เล่มที่ 3 — SP 800-63B: Authentication and Lifecycle Management

เล่มนี้กำหนด requirement สำหรับกระบวนการ authenticate และการจัดการ lifecycle ของ authenticator ครอบคลุม:

- ประเภท authenticator ที่ยอมรับได้ในแต่ละ AAL
- การจัดการ password อย่างปลอดภัย (รวมถึงการห้ามใช้ password ที่อ่อนแอ)
- กฎการเก็บรักษา long-term secret โดย verifier
- การจัดการ session และ lifecycle ของ credential

> **หมายเหตุ:** มี supplement เพิ่มเติม (SP 800-63Bsup1) ที่ครอบคลุมการใช้ **passkey** (syncable authenticator)

---

## เล่มที่ 4 — SP 800-63C: Federation and Assertions

เล่มนี้กำหนด requirement สำหรับ federated identity systems และ assertion ครอบคลุม:

- รูปแบบการทำ federation และการส่ง assertion ระหว่าง trust domain
- ความต้องการของ assertion protocol ในแต่ละ FAL
- การส่ง attribute ของผู้ใช้จาก CSP/IdP ไปยัง RP อย่างปลอดภัย
- แนวทางสำหรับการ query ข้อมูลแบบ privacy-preserving เช่น การถามว่า "อายุมากกว่า X ปีหรือไม่" แทนที่จะส่งวันเกิดจริง

---

## สิ่งที่เปลี่ยนแปลงจาก SP 800-63-2

SP 800-63-3 เป็นการปรับปรุงและปรับโครงสร้างครั้งใหญ่ โดยการเปลี่ยนแปลงสำคัญ ได้แก่:

- **แยก level of assurance** ออกเป็นส่วนอิสระสามส่วน (IAL, AAL, FAL) จากเดิมที่รวมเป็น LOA เดียว
- **แยกเป็น 4 เล่ม** เพื่อให้สามารถปรับปรุงแต่ละส่วนได้โดยไม่กระทบส่วนอื่น
- **ปรับโครงสร้าง identity proofing model** ใหม่
- **เพิ่ม risk assessment methodology** ที่ชัดเจนสำหรับการเลือก xAL
- **เพิ่มข้อกำหนดการเก็บ long-term secret** สำหรับ verifier
- **ส่งเสริม privacy** โดยสนับสนุนการเข้าถึงแบบ pseudonymous และจำกัดการรวบรวมข้อมูล

## ขอบเขตการใช้งาน

แนวทางนี้ครอบคลุมธุรกรรมดิจิทัลทุกประเภทที่ต้องการ digital identity หรือ authentication ไม่ว่าจะเป็นพลเมือง, พันธมิตรทางธุรกิจ, หรือหน่วยงานรัฐบาล

**ข้อยกเว้น:** ธุรกรรมที่เกี่ยวข้องกับ national security system ตามที่กำหนดใน 44 U.S.C. ไม่อยู่ในขอบเขตของเอกสารนี้

ทั้งนี้ แนวทางนี้ไม่ได้กำหนดสถาปัตยกรรม federated identity ให้ใช้แบบใดแบบหนึ่ง แต่เป็น agnostic ต่อรูปแบบที่มีในตลาด เพื่อให้หน่วยงานสามารถเลือกใช้ standards-based, pluggable identity solution ตามความต้องการของภารกิจ
