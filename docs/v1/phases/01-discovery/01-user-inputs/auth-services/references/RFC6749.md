# RFC 6749 — The OAuth 2.0 Authorization Framework

> **Internet Engineering Task Force (IETF)**  
> Request for Comments: 6749  
> Obsoletes: 5849  
> Category: Standards Track  
> Editor: D. Hardt (Microsoft)  
> Published: October 2012  
> ISSN: 2070-1721

---

## Abstract

OAuth 2.0 authorization framework เปิดโอกาสให้ third-party application สามารถขอสิทธิ์เข้าถึง HTTP service ได้อย่างจำกัด ไม่ว่าจะทำในนามของ resource owner โดยผ่านกระบวนการอนุมัติระหว่าง resource owner กับ HTTP service หรือจะอนุญาตให้ third-party application เข้าถึงในนามของตนเองก็ได้

specification นี้ทดแทนและยกเลิก OAuth 1.0 protocol ที่อธิบายไว้ใน RFC 5849

## 1. Introduction

ในรูปแบบ client-server authentication แบบดั้งเดิม client จะขอ access-restricted resource บน server โดยการ authenticate ด้วย credentials ของ resource owner เมื่อต้องการให้ third-party application เข้าถึง restricted resources resource owner จะต้องแชร์ credentials กับ third party ซึ่งก่อให้เกิดปัญหาหลายประการ:

- Third-party application ต้องเก็บ credentials ของ resource owner ไว้เพื่อใช้ในอนาคต (มักเป็น plain-text password)
- Server ต้องรองรับ password authentication แม้จะมีช่องโหว่ด้านความปลอดภัย
- Third-party application ได้รับสิทธิ์เข้าถึง protected resources ของ resource owner มากเกินไป โดยที่ resource owner ไม่สามารถจำกัดระยะเวลาหรือขอบเขตการเข้าถึงได้
- Resource owner ไม่สามารถยกเลิกสิทธิ์ third party รายใดรายหนึ่งได้ โดยไม่ยกเลิกสิทธิ์ทั้งหมด
- การถูกโจมตีที่ third-party application หนึ่งใด ทำให้ password และข้อมูลทั้งหมดรั่วไหล

OAuth แก้ปัญหาเหล่านี้โดยการนำ **authorization layer** มาใช้ และแยกบทบาทของ client ออกจาก resource owner

แทนที่จะใช้ credentials ของ resource owner เพื่อเข้าถึง protected resources, client จะได้รับ **access token** — string ที่แสดงถึง scope, lifetime และคุณสมบัติอื่น ๆ ของการเข้าถึง access token ออกโดย authorization server ด้วยความเห็นชอบของ resource owner และ client ใช้ access token ในการเข้าถึง protected resources บน resource server

> **ตัวอย่าง:** end-user (resource owner) สามารถอนุญาตให้ printing service (client) เข้าถึงรูปภาพใน photo-sharing service (resource server) โดยไม่ต้องแชร์ username/password กับ printing service — แทนที่จะทำเช่นนั้น เธอ authenticate กับ authorization server โดยตรง ซึ่งออก access token ให้แก่ printing service

specification นี้ออกแบบมาสำหรับใช้กับ HTTP ([RFC2616]) เท่านั้น

---

### 1.1. Roles

OAuth กำหนด 4 roles ดังนี้:

| Role | คำอธิบาย |
|------|-----------|
| **Resource Owner** | Entity ที่สามารถให้สิทธิ์เข้าถึง protected resource เมื่อเป็นบุคคล จะเรียกว่า end-user |
| **Resource Server** | Server ที่ host protected resources สามารถรับและตอบสนองต่อ protected resource requests โดยใช้ access tokens |
| **Client** | Application ที่ร้องขอ protected resources ในนามของ resource owner พร้อมการอนุญาต |
| **Authorization Server** | Server ที่ออก access tokens ให้ client หลังจาก authenticate resource owner และได้รับการอนุญาต |

> **หมายเหตุ:** Authorization server และ resource server อาจเป็น server เดียวกัน หรือแยกกัน authorization server เดียวสามารถออก access tokens ที่ยอมรับได้โดย resource server หลายตัว

---

### 1.2. Protocol Flow

```
     +--------+                               +---------------+
     |        |--(A)- Authorization Request ->|   Resource    |
     |        |                               |     Owner     |
     |        |<-(B)-- Authorization Grant ---|               |
     |        |                               +---------------+
     |        |
     |        |                               +---------------+
     |        |--(C)-- Authorization Grant -->| Authorization |
     | Client |                               |     Server    |
     |        |<-(D)----- Access Token -------|               |
     |        |                               +---------------+
     |        |
     |        |                               +---------------+
     |        |--(E)----- Access Token ------>|    Resource   |
     |        |                               |     Server    |
     |        |<-(F)--- Protected Resource ---|               |
     +--------+                               +---------------+
```

**Figure 1: Abstract Protocol Flow**

ขั้นตอนของ flow:

- **(A)** Client ร้องขอ authorization จาก resource owner (โดยตรงหรือผ่าน authorization server เป็น intermediary)
- **(B)** Client ได้รับ authorization grant — credential ที่แสดงถึงการอนุญาตของ resource owner
- **(C)** Client ร้องขอ access token โดย authenticate กับ authorization server พร้อม authorization grant
- **(D)** Authorization server authenticate client, validate grant และถ้าถูกต้องก็ออก access token
- **(E)** Client ร้องขอ protected resource จาก resource server พร้อม access token
- **(F)** Resource server validate access token และถ้าถูกต้องก็ตอบสนองต่อ request

---

### 1.3. Authorization Grant

Authorization grant คือ credential ที่แสดงถึงการอนุญาตของ resource owner ในการเข้าถึง protected resources โดย client ใช้เพื่อขอ access token specification นี้กำหนด **4 grant types**:

#### 1.3.1. Authorization Code

- ใช้ authorization server เป็น intermediary ระหว่าง client และ resource owner
- Client ส่ง resource owner ไปยัง authorization server ซึ่งจะ redirect กลับมาพร้อม authorization code
- Resource owner credentials ไม่ถูกแชร์กับ client
- ให้ประโยชน์ด้านความปลอดภัย เช่น สามารถ authenticate client ได้ และส่ง access token โดยตรงโดยไม่ผ่าน user-agent

#### 1.3.2. Implicit

- Simplified authorization code flow สำหรับ client ที่ implement ใน browser ด้วยภาษา scripting เช่น JavaScript
- Client ได้รับ access token โดยตรง (ไม่ต้องผ่าน authorization code)
- Authorization server ไม่ authenticate client
- Access token อาจถูกเปิดเผยต่อ resource owner หรือแอปอื่น
- ปัจจุบัน **deprecated** (แนะนำให้ใช้ Authorization Code + PKCE แทน)

#### 1.3.3. Resource Owner Password Credentials

- ใช้ username และ password ของ resource owner โดยตรงเพื่อขอ access token
- เหมาะเฉพาะเมื่อมีความไว้วางใจสูงระหว่าง resource owner กับ client เช่น client เป็นส่วนหนึ่งของ OS
- ควรใช้เฉพาะเมื่อไม่มี grant type อื่น
- ปัจจุบัน **deprecated**

#### 1.3.4. Client Credentials

- ใช้ client credentials เป็น authorization grant
- เหมาะสำหรับ machine-to-machine (M2M) เมื่อ client ต้องการเข้าถึง resources ภายใต้การควบคุมของตนเอง
- ต้องใช้กับ **confidential clients** เท่านั้น

---

### 1.4. Access Token

Access tokens คือ credentials ใช้เข้าถึง protected resources เป็น string ที่แสดงถึง authorization ที่ออกให้ client มักจะ **opaque** ต่อ client

- แสดงถึง scope และระยะเวลาของการเข้าถึงที่ resource owner อนุญาต
- มี abstraction layer แทนที่ระบบ authorization หลายรูปแบบด้วย token เดียว
- รูปแบบ, โครงสร้าง และวิธีการใช้งาน access token อยู่นอกขอบเขตของ specification นี้ (ดู [RFC6750])

---

### 1.5. Refresh Token

Refresh tokens คือ credentials ใช้ขอ access tokens ใหม่ เมื่อ access token ปัจจุบันหมดอายุหรือไม่ valid

```
  +--------+                                           +---------------+
  |        |--(A)------- Authorization Grant --------->|               |
  |        |                                           |               |
  |        |<-(B)----------- Access Token -------------|               |
  |        |               & Refresh Token             |               |
  |        |                                           |               |
  |        |                            +----------+   |               |
  |        |--(C)---- Access Token ---->|          |   |               |
  |        |                            |          |   |               |
  |        |<-(D)- Protected Resource --| Resource |   | Authorization |
  | Client |                            |  Server  |   |     Server    |
  |        |--(E)---- Access Token ---->|          |   |               |
  |        |                            |          |   |               |
  |        |<-(F)- Invalid Token Error -|          |   |               |
  |        |                            +----------+   |               |
  |        |                                           |               |
  |        |--(G)----------- Refresh Token ----------->|               |
  |        |                                           |               |
  |        |<-(H)----------- Access Token -------------|               |
  +--------+           & Optional Refresh Token        +---------------+
```

**Figure 2: Refreshing an Expired Access Token**

- Refresh tokens ถูกออกให้ client โดย authorization server
- ใช้ขอ access token ใหม่เมื่อ access token ปัจจุบันหมดอายุ
- Refresh tokens ส่งไปยัง authorization server เท่านั้น **ไม่ส่งไปยัง resource server**
- การออก refresh token เป็น optional ขึ้นอยู่กับ authorization server

---

### 1.6. TLS Version

ทุกที่ที่ specification นี้ใช้ TLS ควรใช้เวอร์ชันที่เหมาะสมตามการ deploy ในวงกว้างและ security vulnerabilities ที่ทราบ ณ เวลาที่เขียน TLS 1.2 เป็นเวอร์ชันล่าสุด

---

### 1.7. HTTP Redirections

Specification นี้ใช้ HTTP redirections อย่างกว้างขวาง ตัวอย่างใน specification ใช้ HTTP 302 status code แต่วิธีอื่นที่ user-agent รองรับก็ได้รับอนุญาต

---

### 1.8. Interoperability

OAuth 2.0 เป็น framework ที่ยืดหยุ่นสูงและมี optional components มาก อาจก่อให้เกิด implementations ที่ไม่ interoperable กัน specification นี้ถูกออกแบบโดยคาดหวังว่างานในอนาคตจะกำหนด prescriptive profiles และ extensions เพื่อให้ interoperable ในระดับ web-scale

---

### 1.9. Notational Conventions

Keywords เช่น "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHOULD", "RECOMMENDED", "MAY", และ "OPTIONAL" ในเอกสารนี้ตีความตาม [RFC2119]

---

## 2. Client Registration

ก่อนเริ่ม protocol, client ต้อง register กับ authorization server ซึ่งมักทำผ่าน HTML registration form

เมื่อ register, client developer ต้อง:
- ระบุ client type ตาม Section 2.1
- ให้ client redirection URIs ตาม Section 3.1.2
- ให้ข้อมูลอื่นที่จำเป็น (เช่น ชื่อแอป, website, logo, ยอมรับ legal terms)

---

### 2.1. Client Types

OAuth กำหนด 2 client types ตาม ability ในการ authenticate กับ authorization server:

**Confidential**
- สามารถรักษา confidentiality ของ credentials ได้
- เช่น web application ที่ run บน secure server

**Public**
- ไม่สามารถรักษา confidentiality ของ credentials ได้
- เช่น native applications หรือ browser-based applications

#### Client Profiles

| Profile | ประเภท | รายละเอียด |
|---------|--------|------------|
| **Web Application** | Confidential | Run บน web server; credentials เก็บอยู่บน server ไม่เปิดเผยต่อ user |
| **User-Agent-Based App** | Public | Code ดาวน์โหลดจาก server และ execute ใน browser; data เข้าถึงได้ง่าย |
| **Native Application** | Public | ติดตั้งและ run บนอุปกรณ์; credentials อาจถูก extract ได้ |

---

### 2.2. Client Identifier

Authorization server ออก **client identifier** ให้ client ที่ register — เป็น unique string แทน registration information

- ไม่ใช่ secret และเปิดเผยต่อ resource owner ได้
- ต้องไม่ใช้ client identifier เพียงอย่างเดียวในการ authenticate
- Unique สำหรับ authorization server นั้น

---

### 2.3. Client Authentication

#### 2.3.1. Client Password

Client ที่มี client password สามารถใช้ HTTP Basic authentication:

```
Authorization: Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3
```

หรืออาจส่ง credentials ใน request body (ไม่แนะนำ):

```
POST /token HTTP/1.1
Host: server.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=tGzv3JOkF0XG5Qx2TlKWIA
&client_id=s6BhdRkqt3&client_secret=7Fjfp0ZBr1KtDRbnfVdmIw
```

#### 2.3.2. Other Authentication Methods

Authorization server อาจรองรับ HTTP authentication scheme อื่น ๆ ตาม security requirements

---

### 2.4. Unregistered Clients

Specification นี้ไม่ห้ามการใช้ unregistered clients แต่อยู่นอกขอบเขต และต้องการการวิเคราะห์ security เพิ่มเติม

---

## 3. Protocol Endpoints

Authorization process ใช้ endpoints ดังนี้:

**Authorization Server Endpoints:**
- **Authorization Endpoint** — client ใช้ขอ authorization จาก resource owner ผ่าน user-agent redirection
- **Token Endpoint** — client ใช้แลก authorization grant เป็น access token

**Client Endpoint:**
- **Redirection Endpoint** — authorization server ใช้ส่ง responses ที่มี authorization credentials กลับไปยัง client ผ่าน resource owner user-agent

---

### 3.1. Authorization Endpoint

ใช้เพื่อ interact กับ resource owner และรับ authorization grant authorization server ต้อง:

- Verify identity ของ resource owner ก่อน
- รองรับ HTTP `GET` method (และอาจรองรับ `POST`)
- **ต้องใช้ TLS**
- Ignore request parameters ที่ไม่รู้จัก

#### 3.1.1. Response Type

Parameter `response_type` ต้องมีค่า:
- `"code"` — สำหรับ authorization code grant
- `"token"` — สำหรับ implicit grant

#### 3.1.2. Redirection Endpoint

Redirection endpoint URI ต้องเป็น absolute URI ไม่มี fragment component

---

### 3.2. Token Endpoint

Client ใช้ขอ access token โดย present authorization grant หรือ refresh token

- ต้องใช้ HTTP `POST` method
- **ต้องใช้ TLS**
- ใช้กับทุก grant type ยกเว้น implicit grant

#### 3.2.1. Client Authentication

Confidential clients ต้อง authenticate กับ authorization server เมื่อ request token endpoint เพื่อ:
- Enforce การ binding ของ refresh tokens และ authorization codes
- ให้สามารถ recover จาก compromised client โดย disable หรือเปลี่ยน credentials
- รองรับ credential rotation

---

### 3.3. Access Token Scope

`scope` parameter แสดงขอบเขตของการเข้าถึง มีรูปแบบ:

```
scope       = scope-token *( SP scope-token )
scope-token = 1*( %x21 / %x23-5B / %x5D-7E )
```

- เป็น space-delimited, case-sensitive strings
- Authorization server อาจปรับ scope ตาม policy
- หากออก scope ต่างจากที่ร้องขอ ต้องระบุ `scope` ใน response

---

## 4. Obtaining Authorization

OAuth กำหนด 4 grant types:

---

### 4.1. Authorization Code Grant

เหมาะสำหรับ **confidential clients** ใช้ authorization server เป็น intermediary

```
     +----------+
     | Resource |
     |   Owner  |
     +----------+
          ^
          |
         (B)
     +----|-----+          Client Identifier      +---------------+
     |         -+----(A)-- & Redirection URI ---->|               |
     |  User-   |                                 | Authorization |
     |  Agent  -+----(B)-- User authenticates --->|     Server    |
     |          |                                 |               |
     |         -+----(C)-- Authorization Code ---<|               |
     +-|----|---+                                 +---------------+
       |    |                                         ^      v
      (A)  (C)                                        |      |
       |    |                                         |      |
       ^    v                                         |      |
     +---------+                                      |      |
     |         |>---(D)-- Authorization Code ---------'      |
     |  Client |          & Redirection URI                  |
     |         |                                             |
     |         |<---(E)----- Access Token -------------------'
     +---------+       (w/ Optional Refresh Token)
```

**Figure 3: Authorization Code Flow**

**ขั้นตอน:**

| Step | รายละเอียด |
|------|------------|
| (A) | Client ส่ง resource owner ไปยัง authorization endpoint พร้อม client_id, scope, state, redirect_uri |
| (B) | Authorization server authenticate resource owner และขอการอนุมัติ |
| (C) | Resource owner อนุมัติ → server redirect กลับพร้อม authorization code |
| (D) | Client แลก code เป็น access token ที่ token endpoint |
| (E) | Authorization server ส่ง access token (และ optional refresh token) กลับ |

#### 4.1.1. Authorization Request

```
GET /authorize?response_type=code&client_id=s6BhdRkqt3&state=xyz
    &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb HTTP/1.1
Host: server.example.com
```

**Parameters:**

| Parameter | Required | รายละเอียด |
|-----------|----------|------------|
| `response_type` | REQUIRED | ต้องเป็น `"code"` |
| `client_id` | REQUIRED | Client identifier |
| `redirect_uri` | OPTIONAL | URI สำหรับ redirect หลัง authorization |
| `scope` | OPTIONAL | ขอบเขตการเข้าถึง |
| `state` | RECOMMENDED | Opaque value ป้องกัน CSRF |

#### 4.1.2. Authorization Response

```
HTTP/1.1 302 Found
Location: https://client.example.com/cb?code=SplxlOBeZQQYbYS6WxSbIA&state=xyz
```

**Authorization Code:** ต้องหมดอายุเร็ว (แนะนำไม่เกิน 10 นาที) และใช้ได้ครั้งเดียวเท่านั้น

#### 4.1.3. Access Token Request

```
POST /token HTTP/1.1
Host: server.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb
```

#### 4.1.4. Access Token Response

```json
{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "example",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "example_parameter": "example_value"
}
```

---

### 4.2. Implicit Grant

> ⚠️ **Deprecated** — ปัจจุบันแนะนำให้ใช้ Authorization Code + PKCE แทน

เหมาะสำหรับ **public clients** ใน browser เช่น JavaScript applications

- Client ได้รับ access token โดยตรงใน URI fragment
- ไม่ออก refresh token
- ไม่ authenticate client

#### 4.2.1. Authorization Request

```
GET /authorize?response_type=token&client_id=s6BhdRkqt3&state=xyz
    &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb HTTP/1.1
Host: server.example.com
```

#### 4.2.2. Access Token Response

```
HTTP/1.1 302 Found
Location: http://example.com/cb#access_token=2YotnFZFEjr1zCsicMWpAA
          &state=xyz&token_type=example&expires_in=3600
```

---

### 4.3. Resource Owner Password Credentials Grant

> ⚠️ **Deprecated** — ใช้เฉพาะกรณีที่ไม่มีทางเลือกอื่น

เหมาะสำหรับกรณีที่ resource owner ไว้วางใจ client อย่างสูง

```
     +----------+
     | Resource |
     |  Owner   |
     +----------+
          v
          |    Resource Owner
         (A) Password Credentials
          v
     +---------+                                  +---------------+
     |         |>--(B)---- Resource Owner ------->|               |
     |         |         Password Credentials     | Authorization |
     | Client  |                                  |     Server    |
     |         |<--(C)---- Access Token ---------<|               |
     +---------+    (w/ Optional Refresh Token)   +---------------+
```

**Figure 5: Resource Owner Password Credentials Flow**

#### 4.3.2. Access Token Request

```
POST /token HTTP/1.1
Host: server.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

grant_type=password&username=johndoe&password=A3ddj3w
```

---

### 4.4. Client Credentials Grant

เหมาะสำหรับ **machine-to-machine (M2M)** เมื่อ client ขอเข้าถึง resources ในนามของตนเอง

- ต้องใช้กับ **confidential clients** เท่านั้น
- ไม่ต้องการ resource owner

```
     +---------+                                  +---------------+
     |         |>--(A)- Client Authentication --->| Authorization |
     | Client  |                                  |     Server    |
     |         |<--(B)---- Access Token ---------<|               |
     +---------+                                  +---------------+
```

**Figure 6: Client Credentials Flow**

#### 4.4.2. Access Token Request

```
POST /token HTTP/1.1
Host: server.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
```

#### 4.4.3. Access Token Response

```json
{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "example",
  "expires_in": 3600,
  "example_parameter": "example_value"
}
```

> **หมายเหตุ:** ไม่ควรออก refresh token สำหรับ client credentials grant

### 4.5. Extension Grants

Client สามารถใช้ extension grant type โดยระบุ grant type ด้วย absolute URI:

```
POST /token HTTP/1.1
Host: server.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Asaml2-bearer
&assertion=PEFzc2VydGlvbiBJc3N1ZUluc3RhbnQ9...
```

## 5. Issuing an Access Token

### 5.1. Successful Response

```
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "example",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "example_parameter": "example_value"
}
```

**Parameters ใน response:**

| Parameter | Required | รายละเอียด |
|-----------|----------|------------|
| `access_token` | REQUIRED | Access token ที่ออกโดย authorization server |
| `token_type` | REQUIRED | ประเภทของ token (เช่น "Bearer") |
| `expires_in` | RECOMMENDED | อายุของ token เป็นวินาที |
| `refresh_token` | OPTIONAL | Token ใช้ขอ access token ใหม่ |
| `scope` | OPTIONAL/REQUIRED | ขอบเขตของ access token |

> Authorization server ต้องส่ง `Cache-Control: no-store` และ `Pragma: no-cache` เสมอ

---

### 5.2. Error Response

```
HTTP/1.1 400 Bad Request
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{
  "error": "invalid_request"
}
```

**Error Codes:**

| Error | รายละเอียด |
|-------|------------|
| `invalid_request` | Request ไม่ถูกต้อง (parameter ขาด, ซ้ำ, ฯลฯ) |
| `invalid_client` | Client authentication ล้มเหลว |
| `invalid_grant` | Authorization grant หรือ refresh token ไม่ valid |
| `unauthorized_client` | Client ไม่มีสิทธิ์ใช้ grant type นี้ |
| `unsupported_grant_type` | Grant type ไม่ supported |
| `invalid_scope` | Scope ไม่ valid หรือเกิน scope ที่ได้รับ |

---

## 6. Refreshing an Access Token

```
POST /token HTTP/1.1
Host: server.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=tGzv3JOkF0XG5Qx2TlKWIA
```

**Parameters:**

| Parameter | Required | รายละเอียด |
|-----------|----------|------------|
| `grant_type` | REQUIRED | ต้องเป็น `"refresh_token"` |
| `refresh_token` | REQUIRED | Refresh token ที่ได้รับมา |
| `scope` | OPTIONAL | ต้องไม่เกิน scope ที่ได้รับจาก resource owner |

Authorization server อาจออก refresh token ใหม่พร้อมกัน (client ต้องทิ้ง token เก่า)

Client เข้าถึง protected resources โดย present access token ให้ resource server วิธีการ present access token อยู่นอกขอบเขตของ specification นี้ (ดู [RFC6750] สำหรับ Bearer Token Usage)

### 7.1. Access Token Types

Access token types กำหนดวิธีที่ client ใช้ token เพื่อ authenticate

### 7.2. Error Response

Resource server ที่พบ error จาก protected resource request ต้องส่ง error response เหมาะสม

## 9. Native Applications

Native applications เป็น public clients ที่ติดตั้งบนอุปกรณ์ของ resource owner มีข้อพิจารณาพิเศษ:

- Credentials ใน application สามารถ extract ได้
- Custom URI schemes ใช้สำหรับ redirection
- ควรใช้ Authorization Code flow ร่วมกับ PKCE (RFC 7636)

## 10. Security Considerations

### 10.1. Client Authentication

Authorization server ควร deploy client authentication ที่แข็งแกร่ง สำหรับ confidential clients

### 10.2. Client Impersonation

Authorization server ต้อง authenticate clients และป้องกัน client impersonation

### 10.3. Access Tokens

- ต้องส่ง access tokens ผ่าน TLS
- ขอบเขตและ lifetime ควร จำกัดเท่าที่จำเป็น

### 10.4. Refresh Tokens

- Refresh tokens ต้องเก็บอย่างปลอดภัย
- Authorization server ควร rotate refresh tokens

### 10.5. Authorization Codes

- Authorization codes มีอายุสั้น (แนะนำ 10 นาที)
- ใช้ได้ครั้งเดียว
- Bind กับ client_id และ redirect_uri

### 10.6. Authorization Code Redirection URI Manipulation

ต้อง validate redirect_uri อย่างเคร่งครัดเพื่อป้องกัน open redirector attacks

### 10.7. Resource Owner Password Credentials

ควรหลีกเลี่ยง grant type นี้เนื่องจาก credentials เปิดเผยต่อ client

### 10.8. Request Confidentiality

ต้องใช้ TLS เสมอสำหรับ authorization และ token endpoints

### 10.9. Ensuring Endpoint Authenticity

ต้องใช้ TLS server-side certificates เพื่อ authenticate endpoints

### 10.10. Credentials-Guessing Attacks

ควรใช้ rate limiting ป้องกัน brute force attacks

### 10.11. Phishing Attacks

ผู้ใช้ควรได้รับข้อมูลที่ชัดเจนเกี่ยวกับ site ที่พวกเขา authenticate

### 10.12. Cross-Site Request Forgery

ใช้ `state` parameter ที่ผูกกับ user session เพื่อป้องกัน CSRF

### 10.13. Clickjacking

ควรใช้ `X-Frame-Options` header ป้องกัน clickjacking บน authorization endpoint

### 10.14. Code Injection and Input Validation

Authorization server ต้อง sanitize inputs ทุกอย่างอย่างเหมาะสม

### 10.15. Open Redirectors

ต้อง validate redirect_uri อย่างเคร่งครัดเพื่อป้องกันการใช้เป็น open redirector

### 10.16. Misuse of Access Token to Impersonate Resource Owner in Implicit Flow

ใน Implicit flow access token อาจถูก misuse เพื่อ impersonate resource owner — นี่เป็นอีกเหตุผลที่ implicit flow ถูก deprecated

## Appendix A. ABNF Syntax

รายการ ABNF syntax สำหรับ parameters สำคัญ:

```
client_id     = *VSCHAR
client_secret = *VSCHAR
response_type = response-name *( SP response-name )
scope         = scope-token *( SP scope-token )
state         = 1*VSCHAR
redirect_uri  = URI-reference
error         = 1*NQSCHAR
grant_type    = grant-name / URI
code          = 1*VSCHAR
access_token  = 1*VSCHAR
token_type    = type-name / URI
expires_in    = 1*DIGIT
username      = *UNICODECHARNOCRLF
password      = *UNICODECHARNOCRLF
refresh_token = 1*VSCHAR
```
